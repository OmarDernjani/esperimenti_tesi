# Code generator vLLM sulla stessa H200

Questo percorso usa la **GPU host 3** per un code generator vLLM in Podman. Il client CPU legge i prompt gia prodotti sul server e invia richieste a `http://127.0.0.1:8000/v1`. Non serve la Spark, un tunnel SSH o ricaricare gli optimizer/adapters.

Prima completare `generate` degli optimizer, poi `podman.sh await-job`. Non avviare training/generazione degli optimizer insieme a vLLM sulla stessa GPU. Il nuovo wrapper blocca l'avvio se trova attivo il container di training configurato, ma non puo identificare tutti i processi indipendenti: controllare anche `nvidia-smi -i 3`.

## Impostazioni persistenti

Lo script legge `../podman.env` e `h200.env` a ogni invocazione. Non servono export nella sessione. In `h200.env` i default sono:

- generatore `Qwen/Qwen2.5-Coder-7B-Instruct`;
- immagine ufficiale `docker.io/vllm/vllm-openai:latest` (puoi fissare tag/digest dopo il pilot);
- GPU 3, server detached `cpo-vllm-h200`, porta locale 8000;
- BF16, contesto totale 16384, budget GPU 0,70 e massimo 4 sequenze;
- cache separata `cpo-vllm-hf-h200`, log per container limitato a 50 MB;
- input `$CPO_OUTPUT/runs`, ereditato dal percorso del training;
- esperimento downstream nuovo `qwen25-coder-7b-h200-v1`.

Se i prompt sono nei vecchi output, modificare in `h200.env` la riga di input con il percorso effettivo, per esempio:

```bash
export CPO_CODEGEN_INPUT="${CPO_CODEGEN_INPUT:-CodePromptOpt/finetuning/outputs/h200/runs}"
```

Se sono in `outputs/runs/`, usare quel percorso. Le variabili gia esportate prevalgono sui default dei file; `config` mostra i valori realmente utilizzati. Modificando il generatore cambiare anche `CPO_CODEGEN_EXPERIMENT` per tenere separati i risultati. Parametri diversi da quelli esposti in `h200.env` richiedono una nuova configurazione esplicita del protocollo.

## Comandi sul server H200

Dalla radice del repository:

```bash
cd /home/agostinelli/esperimenti_tesi

# Verifica percorsi, spazio disponibile e utilizzo GPU
bash CodePromptOpt/finetuning/downstream/h200.sh config
df -h .
nvidia-smi -i 3

# Crea il client Python CPU leggero; non ricostruisce l'immagine di training
bash CodePromptOpt/finetuning/downstream/h200.sh build

# Scarica l'immagine vLLM e avvia il generatore in detached mode
bash CodePromptOpt/finetuning/downstream/h200.sh start
bash CodePromptOpt/finetuning/downstream/h200.sh logs
```

Attendere che il server sia pronto. Ctrl+C chiude solo la visualizzazione dei log. Il primo avvio scarica i pesi base e puo compilare kernel; controllare spazio su disco oltre alla memoria GPU.

```bash
# Verifica l'API senza curl/Python installato sull'host
bash CodePromptOpt/finetuning/downstream/h200.sh ready

# Audit offline dei prompt di un singolo run (non esegue ancora code generation)
bash CodePromptOpt/finetuning/downstream/h200.sh plan --runs qwen3_14b-best-s42

# Pilot: originale, statico, optimizer base e SFT sullo stesso generatore
bash CodePromptOpt/finetuning/downstream/h200.sh run --runs qwen3_14b-best-s42
```

Per l'intera batteria completa:

```bash
bash CodePromptOpt/finetuning/downstream/h200.sh plan --run-glob 'qwen3_4b-*' 'qwen3_8b-*' 'qwen3_14b-*'
bash CodePromptOpt/finetuning/downstream/h200.sh run --run-glob 'qwen3_4b-*' 'qwen3_8b-*' 'qwen3_14b-*'
```

Il client resta in foreground e supporta ripresa tramite SQLite: in caso di errore rilanciare il medesimo comando. Per lunghi job/disconnessioni usare `tmux`. Non usare `podman.sh await-job` per questo client: quel comando gestisce i job di training, non il server vLLM. `--workers 1` riduce la concorrenza lato API. `--split test` va usato solo quando il protocollo e fissato e i file test sono presenti.

Se `/v1/models` fallisce con `Connection reset by peer`, nessun prompt viene inviato in quel tentativo: controllare prima il servizio, non rifare training o generazione dei prompt. Eseguire `h200.sh status` (stato e porta pubblicata), `h200.sh config` (endpoint del client) e `podman logs --tail 100 cpo-vllm-h200`. Un container puo essere in esecuzione mentre vLLM sta ancora scaricando/compilando; aspettare che `h200.sh ready` restituisca il modello. Se invece il server e terminato, diagnosticare il traceback nei suoi log. Dopo un cambio da porta 8000 a 8001, verificare che `CODEGEN_PORT` e la mappatura mostrata da `status` concordino; un export preesistente prevale su `h200.env`. Il client ritenta reset/disconnessioni transitorie, ma non puo riparare un server terminato o una porta errata.

L'assenza/incompletezza dei file prompt ferma le richieste prima di usare la GPU; scegliere run completi. I prompt degenerativi o senza problema restano invariati per evitare selezioni retroattive. L'audit li segnala.

## Identita del generatore e risultati

`start` risolve `CODEGEN_REVISION` a un commit Hugging Face e l'immagine scaricata al suo ID. Salva automaticamente il JSON del client in:

```text
CodePromptOpt/finetuning/outputs/codegen/qwen25-coder-7b-h200-v1/server-config.json
```

Il processo vLLM carica esattamente quel commit e quell'immagine. Se al riavvio cambia l'immagine, il modello o un parametro registrato, lo script rifiuta di riscrivere il config: usare un nuovo `CPO_CODEGEN_EXPERIMENT`, oppure fissare `VLLM_IMAGE` all'ID/digest gia registrato e `CODEGEN_REVISION` al commit gia registrato. Questo impedisce il riuso silenzioso delle vecchie risposte con un generatore diverso.

Se `start` termina subito dopo il download dell'immagine con `exec: "python": executable file not found`, aggiornare `h200.sh`: il controllo del commit nell'immagine vLLM usa `--entrypoint python3`. Non occorre installare Python sull'host o ricostruire l'immagine di training. Rilanciare `start`; i layer gia scaricati vengono riutilizzati.

I file code, l'audit, lo stato e la cache delle risposte sono sotto:

```text
CodePromptOpt/finetuning/outputs/codegen/qwen25-coder-7b-h200-v1/validation/
```

Ogni run contiene `validation-{original,static,base,sft}-code.jsonl`. Il code generator e lo stesso per tutti gli optimizer 4B/8B/14B: non cambia a seconda della dimensione dell'optimizer. Per il default non c'e quantizzazione: BF16. Temperatura 0, seed 42 e budget output 2048 sono registrati nel config automatico.

## Fermare e liberare memoria

Solo dopo che il client ha completato tutte le richieste:

```bash
bash CodePromptOpt/finetuning/downstream/h200.sh stop
nvidia-smi -i 3
df -h .
```

`stop` salva il log in `outputs/codegen/ESPERIMENTO/logs/`, arresta il processo e rimuove il container. La memoria GPU del server viene rilasciata. Risultati e cache dei pesi rimangono. Per cancellare anche i pesi base del code generator dal disco:

```bash
bash CodePromptOpt/finetuning/downstream/h200.sh free-cache
```

Il comando elimina il volume dedicato e rifiuta se e ancora associato a un container. Non tocca adapter fine-tuned, risultati o cache del training. Un avvio successivo riscarichera i pesi. Evitare di pulire volumi mentre un altro processo li sta avviando/usando.

## Test funzionali

Per diagnosticare i fallimenti gia raccolti senza rifare code generation o training, usare [DIAGNOSI.md](DIAGNOSI.md). La nuova sandbox salva stderr/stdout limitati nei risultati nuovi, conservando i punteggi precedenti.

Per i risultati validation locali il file `verified_tests.jsonl` e ora stato preparato nella radice del repository, con mapping verificato di tutti i 10 task e provenienza in `verified_tests.jsonl.mapping.json`. Trasferire entrambi sul server e aggiornare gli script; vedere [CODEGEN_VALIDATION_READY.md](../../reports/CODEGEN_VALIDATION_READY.md). Il wrapper costruisce un'immagine benchmark con NumPy per i controlli HumanEval+. Questo file riguarda solo la validation, non i task test finali.

Ricevere codice non misura ancora pass@1. Quando `verified_tests.jsonl` e disponibile, eseguire la sandbox CPU gia preparata:

```bash
bash CodePromptOpt/finetuning/downstream/evaluate_suite.sh \
  CodePromptOpt/finetuning/outputs/codegen/qwen25-coder-7b-h200-v1/validation verified_tests.jsonl
```

Non e necessario tenere vLLM attivo per eseguire i test. Per formato degli harness e confronti base/SFT vedere [README.md](README.md). Non eseguire il codice generato direttamente sull'host.

Immagini ufficiali e supporto Podman: [documentazione vLLM](https://docs.vllm.ai/en/stable/deployment/docker/). La compatibilita driver/CUDA e la memoria effettiva vanno verificate sul server; questa procedura non installa o modifica il driver dell'host.
